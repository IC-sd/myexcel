## 1. 总结性结论

项目要建设的不是“网页版 Excel”，也不是先做一个固定 ERP，而是：

> 面向开发者、实施者和高级表格用户的开源类 Excel 应用构建平台。应用作者使用表格模板、数据模型、字段绑定、公式、规则和轻量权限配置应用；使用者在类 Excel 界面中录入、粘贴、计算和查询；平台将记录结构化保存，并支持发布、版本、审计和扩展。

产品体验以老 MyExcel 的低学习门槛为起点，以活字格的现代低代码平台结构为主要参照。技术上使用 Univer 提供表格交互底座，但不把 Univer 当作完整业务平台；参考 Nop Entropy 的模型驱动、差量定制和报表思想，但第一阶段不整体引入 Nop，避免形成两个相互竞争的平台内核。

**表间关联是平台核心能力，不是后期附加功能。** Excel/类 Excel 界面负责“怎么看、怎么填、怎么算”，MySQL 负责集中保存和查询数据，平台负责定义并执行“哪些表通过什么字段关联、如何取数和汇总、何时允许回写”。只有把多张业务表连成可运行的业务关系，才能从在线表格走向业务管理平台。

阶段 1 已完成“可配置的表格应用闭环”。后续主线改为公开发布质量、可安装性、通用示例和扩展接口，不以某家公司、行业或内部流程为产品前提。AI、RAG、完整 ERP、专业排产和复杂办公套件能力不进入核心路线；具体场景只作为可替换示例。

### 1.1 产品目标、技术手段与当前成果必须分开

| 层次 | 应当说明什么 | 不能代替什么 |
|---|---|---|
| 产品目标 | 业务负责人配置模板并发布；员工直接在发布后的表格中办理业务 | 不能用数据库/API 清单代替用户工作方式 |
| 产品交互 | 选单元格或区域配置字段、规则和权限；在原模板中填写、粘贴、计算和查看 | 普通字段表单加只读表格预览不能替代主要录入体验 |
| 技术支撑 | 绑定、稳定记录 ID、事务、权威计算、发布隔离和审计 | 这些实现正确，不等于业务人员已经能独立使用 |
| 当前成果 | 已实现且有对应证据的局部能力，注明环境与限制 | 测试数量、构建成功或演示脚本不能代替产品闭环验收 |

普通列表、查询条件、审批待办等可以采用常规页面；限制的是不能让核心单据变成“在另一张普通表单填写，保存后才看原表格”。同样，平台不要求所有业务都无代码：常见模板配置不依赖开发，复杂扩展由专业人员通过受控接口实现。

## 3. 产品定位与边界

### 3.1 产品要解决的问题

1. 表格适合快速表达版式和计算，但文件副本不适合作为多人应用的数据层。
2. 常规 CRUD 低代码项目通常不能保留自由表格版式、公式和批量粘贴体验。
3. 从表格原型到数据库应用之间缺少一个可研究、可运行、可扩展的开源参考实现。
4. 应用作者需要用可视化配置建立字段、主从记录和表间关系，而不是维护散落的 JSON、SQL 和页面代码。
5. 项目贡献者需要清楚的模块边界、合成样例、测试和扩展契约，避免功能演示演变为不可维护的专用系统。

### 3.2 产品应当具备的核心价值

- **低门槛**：熟悉电子表格的用户可以快速使用运行模式，开发者能够用清晰契约扩展平台。
- **数据化**：业务数据进入结构化数据库，而不是继续散落在文件副本中。
- **可持续变化**：模板、规则、权限和流程可以版本化修改和重新发布。
- **兼顾表格与业务系统**：保留表格自由度，同时具备主从数据、权限、流程、审计和事务。
- **计算可扩展**：简单计算继续使用公式；复杂或大规模计算可以迁移到服务端规则或专业引擎。
- **可审计**：重要数据、计算版本、发布版本和操作过程能够追踪。
- **可复现**：克隆仓库后可以用公开文档、合成数据和自动测试复现核心闭环。
- **可扩展**：存储、规则、数据连接和界面扩展通过稳定边界接入，不修改核心即可替换示例。

### 3.3 明确不等于什么

- 不是 Microsoft Excel 的完整替代品；
- 不是以 100% 兼容所有 Excel 特性为目标的 Office 套件；
- 不是只提供在线协作的电子表格；
- 不是固定的排产系统、采购系统、ERP 或公司内部 OA；
- 不是把现有 Excel 文件原样上传后多人共同修改一个 JSON；
- 不是把 Nop、JeecgBoot、NocoBase、Univer 等多个平台简单堆叠；
- 不是以 AI 为核心才能运行的系统。

### 3.4 MySQL、Excel 与“表间关联”分别是什么

用日常业务理解：Excel/类 Excel 界面像员工使用的单据，MySQL 像统一存放业务记录的资料库，表间关联则是单据之间可以共享和使用数据的规则。

| 概念 | 本项目中的作用 | 不能混淆的地方 |
|---|---|---|
| Excel / 类 Excel 界面 | 设计版式、填写、批量粘贴、计算和查看结果 | 一张工作表不必对应一张数据库表；一个页面可以展示多张业务表的数据 |
| MySQL | 集中保存供应商、物料、订单、明细等记录，并执行查询和事务 | 安装 MySQL 不会自动理解哪些业务表应当关联，也不会自动产生业务联动 |
| 表间关联 | 通过确定的字段将记录连接起来，支持取数、查询、汇总以及受控更新 | 不等于复制文件，也不只是跨 Sheet 引用单元格 |
| 平台 | 让设计人员配置上述关系，并在员工操作时执行这些规则 | 不要求员工自己写 SQL 或维护数据库结构 |

例如：供应商资料只在“供应商表”维护；采购单选择供应商后自动带出资料；采购明细选择物料后带出名称、规格和单位；汇总页面按供应商和时间统计采购金额。员工不必在每张表里重复填写相同资料。

需要区分三个层次：

1. **工作表公式引用**：例如 `='物料资料'!B2`，引用的是单元格位置，主要服务于工作簿计算。
2. **业务记录关联**：例如订单通过供应商标识找到对应供应商；即使记录换行、排序或在另一模板中展示，关系仍有效。
3. **业务事件联动**：例如某张单据批准后更新来源单据状态；这是带权限、触发条件和失败处理的操作，不是查询公式。

本项目三者都需要，但重点补齐第二、第三层。不能只证明跨 Sheet 公式能算，就认为表间关联已经完成。以下采购例子用于说明通用能力，不代表已经确定企业的具体采购流程。

## 4. 用户与两种核心视角

平台只有两种核心使用模式。“发布/展示”是设计成果的运行状态，不是第三种模式。

### 4.1 设计模式

主要用户：应用作者、实施者、开发者和模板维护者。

主要职责：

- 创建应用、工作簿和页面；
- 导入现有 Excel 模板或从空白模板创建；
- 创建业务实体、字段、字典和主从关系；
- 配置不同业务表的关联字段、取数条件、汇总口径和更新触发条件；
- 识别并配置固定单元格、重复行、重复列和交叉区域；
- 建立单元格/区域与数据库字段的双向绑定；
- 配置公式、校验、默认值、联动、取数、更新和锁定规则；
- 配置角色、数据范围、字段/单元格权限和操作权限；
- 配置流程、节点、条件、处理人和节点字段状态；
- 使用合成数据或测试数据预览；
- 保存草稿、发布版本、比较版本和回滚；
- 查看运行、错误、性能和审计信息。

### 4.2 运行模式

主要用户：应用使用者、记录处理者和只读查看者。

主要职责：

- 使用已发布的应用和工作簿；
- 像 Excel 一样查看、录入、批量粘贴和修改数据；
- 使用允许的公式、筛选、排序、查找和数据验证；
- 保存一条业务记录或一批业务明细；
- 查询历史记录并回填到原模板版式；
- 选择关联记录后自动带出资料，在权限范围内查看相关单据和汇总结果；
- 发起、审批、退回和追踪流程；
- 查看汇总结果并按权限导出；
- 查看个人或共享范围的记录。

### 4.3 发布与展示的正确位置

发布负责将“设计端草稿”转换成“运行端可用版本”：

```text
设计草稿 -> 校验/测试 -> 发布版本 -> 工作人员运行 -> 新草稿继续修改
                         |                |
                         +-- 固定版本 ----+
```

发布预览属于管理设计端；已发布应用的实际使用属于工作人员端；只读大屏、门户嵌入和公开查看属于运行端的不同呈现方式。

## 5. 核心设计原则

### 5.1 表格是交互界面，数据库是业务事实

工作人员看到的是采购单、周报、排产表或报价单；数据库保存的是业务实体、字段、主从关系和流程状态。系统不应把完整工作簿快照当作唯一业务事实。

核心单据的填写、批量粘贴、允许公式、关联选择和保存反馈，应发生在发布后的模板版式中。记录列表用于查找和打开单据，只读投影用于查看历史或结果，两者不能充当可编辑模板缺失的替代验收。内部表名、字段 ID、存储命名空间和 SQL 不应成为普通工作人员的操作前提。

### 5.2 模板与数据分离

- 模板定义版式、公式、控件、绑定和规则；
- 业务记录保存具体数据；
- 打开记录时将业务数据投影回模板；
- 模板升级不能无控制地覆盖历史业务数据；
- 历史记录必须知道自己使用的模板版本和计算版本。

### 5.3 配置优先，代码兜底

常见业务通过可视化配置完成；复杂场景允许扩展函数、服务端规则、SQL/API 连接器或专业计算插件，但扩展必须通过受控接口进入平台，不能把脚本任意散落在单元格和页面中。

设计端以业务名称、单元格/区域选择和规则选项组织操作，技术标识由平台管理。验收时不能通过编辑源码、JSON、SQL 或初始化脚本代替设计人员创建第二个模板；开发者预置演示只证明样例可运行，不证明低门槛配置已经实现。

### 5.4 前端即时反馈，服务端最终负责

浏览器公式提供类似 Excel 的即时体验；涉及金额、库存、交期、流程条件、权限和最终结果的关键计算，由服务端重新验证或计算后再持久化。

### 5.5 小闭环优先

每一阶段必须形成可运行、可验证的纵向闭环，不能只完成界面、只完成数据库或只完成技术底座。

任务按“用户动作 → 平台行为 → 数据与权限结果 → 实际验证”组织；技术层可拆为子任务，但不能各自通过后直接推定端到端通过。当前缺陷修复与尚未实现的新能力分开列项；前者收敛不等于后者完成，也不能以“修复体验”为名直接扩大开发范围。

### 5.6 本地优先、部署可迁移

当前开发验证以 Windows 本地进程和本地数据库为主，Docker 不是前置条件。架构与配置应保持可迁移，后续可部署到 Linux、虚拟机、容器或企业内网服务器。

### 5.7 不以缺少真实数据为停工理由

平台能力使用合成数据、匿名示例和测试模板验证；真实数据只用于后续业务适配和最终验收，不应成为平台底座开发的前置阻塞。

## 6. 从设计到运行的完整业务链路

```text
创建应用
  -> 新建/导入表格模板
  -> 建立数据模型
  -> 配置单元格/区域绑定
  -> 配置公式、规则、数据源
  -> 配置权限和流程
  -> 使用测试数据预览
  -> 发布固定版本
  -> 工作人员录入/粘贴/计算
  -> 服务端校验和权威计算
  -> 事务保存业务记录
  -> 查询、回填、审批、报表、导出
  -> 根据反馈创建下一版草稿
```

平台必须同时打通“设计链路”和“运行链路”。只有可以配置但无法稳定运行，或只有表格编辑但无法绑定业务数据，都不算平台闭环。

面向使用者，这条链路应表现为：设计人员制作并发布表格应用，工作人员在该模板内填报和处理业务，管理人员按权限查结果与进度。中间的数据建模、字段绑定和服务端计算应由配置和平台执行衔接，不要求员工在表格、数据库工具和开发脚本之间切换。

## 7. 功能架构

### 7.1 应用与导航

- 应用、模块、菜单、页面和工作簿管理；
- 应用所有者、维护者和访问范围；
- PC 页面优先，保留移动端和门户嵌入能力；
- 应用复制、导入、导出和归档。

### 7.2 表格模板设计

- 多工作表、行列、合并单元格、样式和冻结窗格；
- 固定单元格、重复行、重复列和交叉区域；
- 文本、数字、日期、选项、附件等通用控件；
- 数据验证、条件格式和隐藏/只读区域；
- 模板参数、页面变量和上下文变量；
- XLSX 导入作为辅助起点，不承诺无损支持所有特性。

### 7.3 数据模型

- 业务实体、字段、主键、唯一约束和索引；
- 一对一、一对多和多对多关系；
- 主表/明细表；
- 字典、状态和引用字段；
- 系统字段：创建人、创建时间、修改人和版本等；
- 物理表与逻辑模型的迁移记录。

### 7.4 字段与区域绑定

绑定类型至少包括：

1. 固定单元格绑定：如 `B3 -> purchase_order.supplier_id`；
2. 固定区域绑定：一个区域对应一个复合对象；
3. 纵向重复绑定：明细行向下扩展；
4. 横向重复绑定：日期、周期等向右扩展；
5. 二维交叉绑定：人员 × 日期、产品 × 月份等；
6. 查询/显示绑定：只读回填或聚合结果；
7. 参数绑定：当前用户、组织、日期和流程上下文。

绑定必须定义方向：读取、写入或双向；同时定义空值、类型转换、冲突、增删明细和保存策略。

这里的“绑定”与“表间关联”是两件事：绑定解决“页面的这个格子显示或保存哪个字段”；表间关联解决“当前订单如何找到供应商、明细、来源单据和汇总数据”。两者由平台衔接，不能用保存一份字段配置替代实际取数和写入。

### 7.5 公式与规则

- Excel 兼容公式；
- 跨 Sheet 引用；
- 自定义业务函数；
- 数据校验规则；
- 默认值和自动编号；
- 字段/单元格联动；
- 跨记录查询和聚合；
- 可视化配置表间取数、关联查询、分类汇总和有明确触发条件的回写规则（见第 8.2、8.3 节）；
- 保存前、保存后、提交前、审批后等事件规则；
- 规则依赖图、循环引用检测和错误定位。

### 7.6 数据源与集成

- 平台内部业务数据库；
- 平台配置的数据查询；
- Excel/CSV 导入；
- HTTP/JSON API；
- 后续受控开放 SQL、消息、文件和第三方系统连接器；
- 数据源凭据必须由服务端保管，不能下发到浏览器模板。

### 7.7 发布与版本

- 草稿、测试、已发布、停用和归档状态；
- 模板版本、数据模型版本、规则版本和流程版本；
- 发布前自动检查；
- 发布快照和回滚；
- 数据结构迁移计划；
- 历史记录与创建时版本关联；
- 发布差异说明和影响范围。

### 7.8 权限

权限层级：

```text
应用 -> 页面/工作簿 -> 数据表 -> 行/记录 -> 字段/单元格 -> 操作
```

核心权限对象：用户、角色、记录范围和状态流参与人。组织、岗位和租户模型不作为核心路线的前置能力，可由扩展实现。

节点状态：隐藏、只读、可编辑、必填和可执行。前端状态只负责体验，服务端必须独立执行同等权限检查。

### 7.9 工作流

- 流程绑定业务记录，不绑定孤立 Excel 文件；
- 支持提交、审批、退回、撤回、转交、会签、条件分支和结束；
- 节点可以改变字段/单元格的可见、只读、可编辑和必填状态；
- 流程版本与运行实例分离；
- 第一阶段先完成简单可用的状态流，后续再决定是否接入完整 BPMN 引擎。

### 7.10 查询、报表与导出

- 业务记录列表和保存的查询方案；
- 表格回填、汇总和交叉展示；
- XLSX、CSV 和 JSON 导入导出；
- 运行报表与设计模板分离；
- 图表、PDF 和打印不进入核心路线；有明确社区需求时通过扩展实现，不与在线录入内核强绑定。

### 7.11 运维与审计

- 登录、配置、发布、权限、数据修改和流程操作审计；
- 公式错误、导入错误和服务端任务日志；
- 模板与数据备份；
- 性能统计、慢公式和慢查询；
- 健康检查和故障恢复。

## 8. 核心领域模型

目标模型不应只有 `workbooks.snapshot`，至少需要以下边界：

| 领域 | 核心对象 | 说明 |
|---|---|---|
| 应用 | Application、Module、Page | 业务应用和导航 |
| 模板 | WorkbookTemplate、SheetTemplate、TemplateVersion | 工作簿版式与版本 |
| 表格 | Cell、Range、Style、Validation、NamedRange | 表格交互模型 |
| 数据 | Entity、Field、Relation、Dictionary | 业务数据模型 |
| 绑定 | CellBinding、RangeBinding、RepeatBinding | 表格与数据之间的桥梁 |
| 表间关联 | RelationDefinition、QueryDefinition、AggregationDefinition、WritebackRule | 稳定记录关系、取数、汇总与受控联动；关系复用数据模型中的 Relation 定义，不另建一套冲突模型 |
| 计算 | Formula、BusinessRule、Function、Dependency | 公式与规则 |
| 运行 | BusinessRecord、RecordItem、RecordVersion | 真实业务记录 |
| 流程 | ProcessDefinition、ProcessInstance、Task | 流程定义与实例 |
| 权限 | Role、Policy、DataScope、FieldPolicy | 访问控制 |
| 发布 | Release、Migration、Rollback | 发布和结构迁移 |
| 审计 | AuditEvent、CalculationLog、ImportLog | 可追踪性 |

### 8.1 示例：采购订单

```text
WorkbookTemplate: 采购订单
  Sheet: 采购申请单
    B3 -> PurchaseOrder.supplierId
    F3 -> PurchaseOrder.orderDate
    A7:F30 -> PurchaseOrder.items[]
      B列 -> PurchaseItem.materialCode
      D列 -> PurchaseItem.quantity
      E列 -> PurchaseItem.price
      F列 -> quantity * price
```

保存时执行：

1. 从绑定单元格读取主表和明细数据；
2. 类型转换与必填校验；
3. 服务端重新计算关键字段；
4. 在一个数据库事务中保存主表和明细；
5. 写入模板版本、计算版本和审计；
6. 返回服务器最终结果并刷新相关单元格。

### 8.2 表间关联的设计与使用

#### 8.2.1 关系是记录之间的连接，不是格子位置

```text
供应商表（supplier.id）
    └──采购订单（supplier_id -> supplier.id）
           └──采购明细（order_id -> order.id）
                  └──物料资料（material_id -> material.id）

采购订单 + 明细 -> 按供应商/日期/物料查询和汇总 -> 不同模板与报表展示
```

- 一家供应商可以对应多张订单；一张订单可以有多条明细。
- 多条明细可以引用同一物料，不需要各自维护一份物料档案。
- 关系使用稳定标识，不使用行号或可能重名的显示名称连接记录；业务编码用于选取、显示或受约束的匹配。
- 同一个业务实体可以被多个工作表、模板和报表引用，不以文件路径互相链接，也不要求用户同时打开相关工作簿。
- 一对一、一对多属于基础能力；多对多使用中间关系实体表达，复杂关系配置在阶段 2 扩展。

#### 8.2.2 设计人员如何配置

设计端提供“表间关联”入口，用业务语言完成：

1. 选择当前表与被关联表，例如“采购订单 -> 供应商”。
2. 指定匹配字段及单条/多条关系，例如“订单的供应商 -> 供应商编号”。平台保存稳定标识引用。
3. 选择取回字段，例如名称、联系人；配置筛选条件、排序和是否允许手工覆盖。
4. 选择取数用途：下拉选择、自动带出、明细列表、汇总数值或相关单据入口。
5. 对需要更新其他记录的规则，单独选择触发事件、目标记录和允许更新的字段。
6. 预览结果，检查无匹配、多匹配、权限不足和循环依赖；发布时固定规则版本。

常用关联不要求设计人员编写 SQL。高级查询作为受控扩展，不作为普通模板配置的前提。

#### 8.2.3 平台提供的四种表间能力

| 能力 | 示例 | 数据是否被修改 |
|---|---|---|
| 关联取数 | 选择物料后带出名称、规格、单位 | 查询本身不改来源数据；带出值是否保存按绑定策略决定 |
| 关联查询 | 从订单查看所属供应商、明细和来源记录 | 否 |
| 关联汇总 | 按供应商、月份汇总有效订单金额 | 否；需要缓存时必须标注刷新状态 |
| 受控回写/生成 | 审批成功后更新来源申请的处理状态，或按规则生成下游单据 | 是；必须经过独立授权、校验和审计 |

“表间公式”是业务人员配置取数、汇总和更新规则的入口，不应混同为所有操作都由 Excel 单元格公式执行。特别是读数据的公式不得偷偷修改其他业务记录。

### 8.3 表间关联的执行约束

#### 8.3.1 数据变化并非全部实时同步

每条取数规则必须选择策略：

- **实时引用**：读取当前来源数据；按打开、选择、刷新或依赖变化等事件重新取数。
- **取数快照**：将选定时的值存入业务记录；适合已确认单据的名称、单价等历史口径。
- **事件回写**：保存、提交或审批成功时执行明确更新；查看页面和普通重算不触发写入。

例如，物料参考价格改变，不应自动重写已批准订单的成交单价。模板设计者必须能区分“当前资料”和“当时业务事实”。允许刷新草稿价格时，应显示差异并按规则确认。

#### 8.3.2 权限、异常与一致性

- 关联查询、下拉选项、汇总和导出均在服务端限制数据范围；不能通过取数或汇总绕过无权查看的表或字段。
- 单条关联出现多个匹配时应阻止或要求明确选择，不能随意取第一条；必需关联缺失时阻止保存。
- 区分“没有记录”“数值为零”“无权限”“取数失败”；不能把后两者显示成正常的空值或零。
- 被引用记录删除时默认限制删除或停用；级联删除必须另有明确业务配置，不自动删除历史单据。
- 回写明确目标字段、业务状态和更新条件；已完成或锁定记录不得被任意覆盖。
- 同一数据库内的联动写入采用事务、版本校验和幂等控制；重复提交不得重复生成单据或重复累加。
- 跨系统写入不假定存在同一事务；留到阶段 2 通过任务、重试和对账处理，不能在部分失败时报告全部成功。
- 建立规则依赖与触发链，防止 A 更新 B、B 再更新 A 的循环；日志记录触发事件、规则版本、来源与目标记录、结果及失败原因。
- 查询采用有界范围、分页和批量取数，避免每个单元格各请求一次数据库；汇总在服务端按相同权限口径处理。

#### 8.3.3 第一阶段的最小验证范围

使用合成的供应商、物料、订单和订单明细，完成“选择关联记录 -> 自动带出 -> 保存 -> 重新打开 -> 关联查询 -> 按条件汇总”。另用一组简化的来源/目标测试记录验证一次审批触发回写，不扩展成完整采购或库存模块。

验收重点是这些行为能够由设计配置驱动，并在另一个模板中复用，而不是为一张采购单写死业务代码。复杂跨系统同步、多对多编辑和多级单据链留到阶段 2。

## 9. 计算架构

复杂 Excel 样本证明，不能把所有业务规则永久留在超长单元格公式中。计算体系分为三层。

### 9.1 第一层：前端表格公式

用途：即时反馈、简单汇总、临时分析和熟悉的 Excel 操作体验。

适合：

- 同一记录内的加减乘除；
- 常见 IF、SUM、COUNT、日期、查找等函数；
- 用户在允许区域内编写的辅助公式；
- 不作为唯一权威依据的展示计算。

### 9.2 第二层：服务端权威规则

用途：保存、提交、审批和批量任务时进行一致、可审计的计算。

适合：

- 金额、库存、成本、交期和状态；
- 跨记录查询和聚合；
- 数据校验、表间更新和事务；
- 权限条件和流程分支；
- 需要统一计算版本的业务规则。

### 9.3 第三层：专业计算插件

用途：排产、优化、仿真、大批量重算等专业问题。

适合：

- 多约束排产；
- 三个月滚动资源计算；
- 大量依赖和迭代优化；
- 需要后台任务、并行计算或专门算法的场景。

专业引擎通过稳定的输入/输出契约接入，表格负责配置、查看、人工调整和解释结果，而不是承担全部算法。

### 9.4 公式兼容矩阵

每个函数或 Excel 特性应记录：

| 项目 | 内容 |
|---|---|
| Excel 名称 | 如 `SUMIFS` |
| 前端支持 | 支持/部分支持/不支持 |
| 服务端支持 | 支持/替代实现/不支持 |
| 导入导出 | 可往返/仅保留/丢失 |
| 权威性 | 展示计算/服务端复算 |
| 性能限制 | 推荐规模与已知边界 |
| 测试样例 | 输入、公式、期望结果 |

对于不支持的公式，平台应提示、保留原公式或提供替代迁移建议，不能静默计算错误。

## 10. 合成工作簿兼容性基准

公开项目不保存或引用用户提供的工作簿。兼容与性能验证使用仓库脚本生成的合成样本，固定覆盖以下结构：

| 维度 | 合成基准 |
|---|---|
| 行数 | 100、1,000、10,000 |
| 宽度 | 普通表及约 200 列宽表 |
| 工作表 | 单 Sheet 与多 Sheet |
| 公式 | 基础算术、条件、聚合、查找、日期和跨 Sheet 引用 |
| 版式 | 合并、冻结、筛选、样式和隐藏状态 |
| 数据 | 随机种子可固定、无个人或公司信息、可重复生成 |

### 10.1 对平台设计的直接影响

1. **宽表渲染**：验证约 200 列的横向滚动、冻结、定位和可视区域渲染。
2. **公式兼容**：以明确矩阵和可重复样本扩展函数，不盲目追求函数数量。
3. **依赖计算**：逐步补充依赖图、增量重算和慢公式定位；后台重算按实际需求引入。
4. **数据与展示分离**：结构化记录不依赖工作表行号，宽表只是数据投影方式之一。
5. **回归可公开**：所有兼容样本均可提交、可生成、可审查，不使用外部或私人文件作为 CI 前提。

### 10.2 暂不承诺

项目不承诺任意 `.xls/.xlsx` 可以无损导入，也不承诺宏、外部链接、命名区域、数组公式、图表、透视表和打印设置。导入必须给出兼容报告，不能静默产生错误结果。

## 11. 总体技术架构

### 11.0 共同开发必须遵守的技术基线

本节是当前协作开发的统一约定，不只是可选技术介绍。参与者在同一项目内沿用下表，不自行另建前端、后端、数据库访问或权限体系。范围仅限已授权任务；统一技术栈不等于恢复暂停的新功能开发。

下表依据 2026-09-04 的 [package.json](../package.json)、[package-lock.json](../package-lock.json) 和源码核对。它是现有项目的协作基线，不是“最新版本推荐”或完整平台已实现声明。

| 层面 | 统一技术及版本 | 用途与边界 |

| 语言与模块 | JavaScript、ES Modules | 前端 `.vue` / `.js`，后端与共享契约 `.mjs`；当前无 TypeScript 编译体系，不自行混入另一语言工具链 |
| Node.js | 协作对齐 24.19.0 | 本轮实际运行版本；package.json 仅声明 `>=24`，并未自动锁定版本。成员先对齐此版本，不将 `>=24` 解释为可各用不同主版本 |

| 前端应用 | Vue 3.5.21 | Single File Component、`<script setup>`、Composition API；业务页面统一 Vue |

| 页面样式与状态 | 原生 CSS、Vue 响应式状态 | 现有 `src/styles.css` 和 Vue 组件；尚未采用统一第三方 UI 库、Pinia 或 Vue Router，不能各自引入不同方案 |
| 前端请求 | 浏览器 fetch，统一 `src/api.js` | 同源 `/api`；普通 JSON 与文件传输沿用现有封装，不在组件散落另一套 HTTP 客户端 |
| 后端服务 | Node.js `node:http` | 当前为模块化单体原型，无 Express/Nest/Spring Boot；新接口沿用现有路由与服务分层 |
| 原型元数据 | Node 内置 `node:sqlite` | `DatabaseSync` 管理模板、身份、会话等；SQLite 随 Node 运行时，不另选 npm SQLite 驱动；双库为过渡事实，非长期架构批准 |
| 业务数据 | MySQL 8.4.11；mysql2 3.24.3 | MySQL 版本来自已有隔离环境验收；统一 `mysql2/promise` 连接池、InnoDB 和现有 SQL 迁移，不各自引入 ORM |
| Excel 文件转换 | SheetJS xlsx 0.20.3 | 来源固定为 package.json 中的官方 tgz URL，使用现有 workbook-codec.mjs；不能只按包名安装其他版本，不承诺全量 Excel 兼容 |
| 测试 | Node `node:test`、`node:assert/strict` | API、存储、契约及组件逻辑测试放 `tests/`；Vue 编译/SSR 辅助沿用当前夹具和锁定依赖；不把组件测试当真实浏览器验收 |
| 版本管理与本地运行 | Git、Windows PowerShell；无 Docker 前置要求 | 源码与文档入库，依赖/秘密/运行数据库排除；启动及环境操作只维护在 [环境说明](../../environment/README.md) |

直接依赖以 package.json 的精确声明为准，完整依赖树以 package-lock.json 为准；版本表是团队阅读入口，不替代锁文件。变更须同时更新受影响的版本表、manifest、lock 和验证记录，不能“文档一套、实际安装一套”。Node/npm 当前仅为文档约定，没有新增自动版本检查或 CI 强制门禁。

### 11.1 前端

- 当前继续采用 Vue 应用外壳；
- Univer 承担表格模板设计及工作人员核心单据的录入、计算与回填交互，不仅是保存后的预览器；
- 普通管理页、查询页、流程中心不强制使用表格；
- 表格组件通过适配层访问应用模型和业务数据，避免页面直接依赖数据库结构；
- 大工作簿采用按需加载、可视区域渲染和分片数据策略；
- 不将数据源凭据、服务端权限规则和权威计算逻辑放入前端。

### 11.2 后端

后端应逐步拆分清晰的模块边界：

- 身份与组织；
- 应用与模板；
- 数据模型与迁移；
- 绑定与运行记录；
- 表间关联、查询、汇总与受控回写（统一经过业务数据服务，不允许表格直接连接 MySQL）；
- 公式与规则；
- 发布与版本；
- 权限；
- 工作流；
- 文件导入导出；
- 审计与运行任务。

第一阶段可以保持单体应用，但代码、表结构和 API 要按模块边界组织，避免后续迁移时全部重写。

### 11.3 数据存储

- MySQL：平台元数据、业务数据、发布记录、权限和审计；
- Redis：会话、缓存、锁、任务状态和通知；
- 文件存储：导入文件、附件、模板源文件、导出物和备份；
- SQLite：仅保留为原型或单机开发数据，不作为企业运行目标数据库。

### 11.4 工作流选择

第一阶段先实现统一流程接口和简单状态流，验证流程与表格字段权限联动。达到 BPMN、会签、流程版本和复杂路由需求后，再评估 Flowable 或现有后端自带流程模块。业务代码不能直接绑死某个引擎 API。

### 11.5 Nop 的位置

Nop Entropy 当前作为设计思想和局部技术候选：

- 借鉴 Excel 模型、元模型、代码生成和差量定制；
- NopReport 可做独立复杂报表试验；
- 不在第一阶段让 Nop 与现有后端同时管理 ORM、权限、流程和页面元数据；
- 只有独立验证证明收益大于集成复杂度后，才通过本文件的决策记录调整。

### 11.6 模块职责和协作接口

| 位置 | 负责什么 | 协作约束 |
|---|---|---|
| `src/components/`、`src/styles.css` | 两种使用视角、表格交互和页面反馈 | 业务页面统一 Vue；界面权限只负责显示，不能替代服务端鉴权 |
| `src/api.js` | 前端接口调用和错误解析 | 新接口先约定方法、路径、请求/响应和错误，再同步后端与测试 |
| `shared/business-model.mjs`、`shared/record-editor.mjs` | 模型、字段、主从绑定、提取/回填和记录编辑契约 | 前后端复用同一契约，不能各自定义不兼容的字段、ID 或模型版本 |
| `server/app.mjs`、`server/business/runtime-api.mjs` | HTTP 路由、会话/权限检查、参数解析和响应 | 沿用 `/api/auth`、`/api/workbooks`、`/api/runtime` 的现有边界；不绕过业务服务直接拼接数据库写入 |
| `server/business/records.mjs`、`mysql.mjs`、`migrations/` | 业务记录、关联、事务、连接池和结构迁移 | 数据访问集中管理；迁移顺序和校验和统一，已应用迁移不得就地改写 |
| `server/store.mjs`、`workbook-codec.mjs` | 原型元数据与版本、XLSX 转换 | 保留现有过渡边界，不另建一套身份或工作簿持久化实现 |
| `tests/`、`tests/fixtures/` | 回归及隔离合成样本 | 共用测试方式与契约；不得向当前演示库或真实库灌入测试数据 |

接口和数据约定：

1. 接口以现有 HTTP/JSON 为主，文件上传/下载沿用既有二进制接口；统一通过 `src/api.js` 接入。不额外发明与当前返回对象不兼容的统一包装，兼容性变化先评审。
2. 身份沿用当前服务端会话与同源 cookie；不自行并行接入 JWT/SSO。接口错误沿用 HTTP 状态和 `{ error: ... }` 信息；具体负载以相关路由和测试为准，新增异常必须有对应前端处理。
3. 主从记录和关联使用稳定 ID，不用行号、名称或格子位置充当业务主键；已发布模板/记录版本、幂等标识、所有者权限沿用现有契约。
4. 定点金额按现有十进制文本及精度约束传输和保存，不在其他模块改用浮点金额；当前日期字段沿用 `YYYY-MM-DD` 文本。新增类型先修改共享校验和回归用例。
5. 单次主从业务写入、关联、审计和幂等结果使用既有 MySQL 事务；不能把 SQLite/MySQL 两库操作称为同一事务。跨库迁移/联合恢复仍须单独设计和验证。
6. 源码风格沿用邻近文件及 `.gitattributes`：JavaScript/SQL/Markdown 等为 LF、PowerShell 为 CRLF，文件使用 UTF-8。当前没有统一 ESLint/Prettier 门禁，不声称已配置；不得借功能提交批量重排无关文件。

### 11.7 成员接入、验证与技术变更门槛

1. 接入前阅读本节、补充要求和进度第 2—6 节，确定共同基线提交、任务范围及负责模块。Node/npm 对齐第 11.0 节；MySQL 使用隔离实例，不能共享真实数据做开发。
2. 复用已有依赖；首次安装或锁文件变化时，先按 R-007 核对依赖变更与兼容性，再按锁文件使用 `npm.cmd ci`。它会重建 node_modules 且可能联网，本次没有执行；不要直接运行无版本的安装或自动升级。
3. 独立任务使用独立分支/工作目录，默认新分支以 `codex/` 开头，不重命名现有 `phase1/foundation`。任务开始登记共同契约及模块归属；多人修改共享模型、路由或锁文件时先协调，避免各自实现同一能力。
4. 代码交付至少运行相关回归和 `npm.cmd run build`，并记录实际命令/结果。测试入口是 `npm.cmd test`；MySQL 专项须启用 `MYEXCEL_MYSQL_TEST=1` 且验证隔离实例，跳过不能记作通过。真实页面改动还需实际交互证据，不能由构建/SSR 代替。
5. 合并前对齐目标分支，检查接口和数据契约兼容、迁移影响、失败路径、权限与测试；按明确文件提交，记录未覆盖项。当前未配置远程协作/CI，远程地址、上传、分支保护及合并负责人应先协调，不能自行推送。
6. 增加/替换框架、UI 库、ORM、数据库、语言或包管理器，以及依赖升级，均先在本文件写明理由、兼容影响、下载量、迁移/回退及验证方法，在进度中登记有界计划；重大取舍经用户确认后统一变更，禁止成员私自形成平行栈。

当前不选用清单：Java/JeecgBoot 保留为未来后端演进待决策项，不是现在可并行开发另一后端的许可；Nop、Flowable、Redis 接入及其他企业组件均未因本节而获准安装或开发。将来若批准迁移，统一更新技术基线和接口过渡计划；批准之前所有当前协作仍沿用第 11.0 节。

## 13. 阶段路线

阶段编号表示产品演进顺序，不再按旧 ERP 模块顺序把所有需求同时塞入。

### 阶段 0：环境与基线

目标：确认开发、测试和运行基础可用。

范围：

- 本地 Node、Java、数据库和缓存；
- 前后端启动、测试、构建；
- 示例数据和测试账号；
- 环境检查脚本；
- 文档与目录结构。

状态：已有基础，但后续仍需按最终后端选择统一整理。Docker 不是完成条件。

### 阶段 1：平台最小业务闭环（已完成基线）

已实现范围、当前任务及后续顺序统一见 [当前交接包](PHASE1_PROGRESS.md#2-当前交接包) 和 [当前任务](PHASE1_PROGRESS.md#4-当前任务与后续顺序)，验证摘要见第 5 节。本节只定义完整阶段要求，不复制实时进度。

目标：让设计人员通过配置创建具备表间关联能力的表格业务应用，并让工作人员直接在发布后的模板中填报、计算、查询和处理业务。数据库支撑这一体验，第一阶段不能停留在单张表内部计算或独立的普通表单 CRUD。

必须完成：

1. 应用、模板、Sheet 和模板版本；
2. 数据实体、字段、字典和主从关系；
3. 固定单元格和纵向重复明细绑定；
4. 文本、数值、日期、选项等基础控件；
5. 基础 Excel 公式和服务端关键字段复算；
6. 主表/明细表事务保存；
7. 业务记录列表、查询、打开和回填；
8. 草稿、发布、固定版本和回滚；
9. 管理设计端与工作人员端；
10. 应用/模板/记录/字段的基础权限；
11. 提交、通过、退回的简单流程；
12. 操作、发布、数据和流程审计；
13. XLSX 导入提示和导出；
14. 合成业务模板的端到端验收。
15. 同库业务表之间的稳定关系、选择取数、条件查询和分组汇总；
16. 一条可配置的审批事件回写规则，包含权限、事务、幂等和日志；不扩展完整采购/库存业务模块。

推荐首个验证模板：采购申请单或费用报销单。理由是可以完整验证主表、明细、公式、权限、流程和回填，同时避免排产算法干扰平台基础判断。

阶段 1 完成标准：不修改代码，仅通过设计端配置和发布，能够创建并运行第二个结构相近的业务模板，并复用已有的基础资料关联、取数和汇总规则。表间关联必须有实际运行证据，不能以保存了关联配置或跨 Sheet 公式能计算代替。

上述完整范围继续保留。各小阶段按依赖逐批实现、验收和打磨，不能把未完成项移到阶段 2 或降低验收标准；“当前成果收敛通过”只形成原型检查点，不构成阶段 1 通过。

### 阶段 2：公开发布基线

目标：把已完成的本地闭环整理成任何开发者都能安全获取、理解、启动和验证的 GitHub 项目。

必须完成：

1. **公开前清理**：移除公司名称、内部标题、账号、绝对路径、远程地址说明和非公开参考材料；扫描当前文件、构建产物、日志和 Git 历史。现有私有仓库保留作历史归档，公开仓库优先使用经过清理的单一初始基线，不能直接公开包含旧信息的历史。
2. **通用身份**：界面、包名、文档和合成数据统一使用中性项目标识；正式项目名和图标在重名及许可证检查后确定，确认前使用“通用类 Excel 应用构建平台”作为暂名。
3. **快速启动**：提供跨平台 Node 启动入口；默认演示模式不依赖私有路径或预装服务，使用可丢弃的本地存储和可重复生成的合成数据。MySQL 作为可选持久化适配器保留，不要求初次体验者先搭企业环境。
4. **仓库基础**：确定兼容依赖的开源许可证，并提供 `LICENSE`、`NOTICE`、`CONTRIBUTING`、`SECURITY`、行为准则、Issue/PR 模板和清晰目录说明。
5. **持续集成**：GitHub Actions 在干净环境执行依赖安装、自动测试和生产构建；Pull Request 不依赖维护者本机数据库或秘密。
6. **通用示例**：以联系人目录、项目跟踪和订单明细等完全合成模板组成最小示例库；示例可删除、可重建，不出现特定公司或真实业务背景。
7. **首个公开版本**：提供截图或短演示、功能矩阵、已知限制、升级说明和可验证的 release 包；不承诺云服务、企业支持或完整 Excel 兼容。

阶段 2 明确不做：组织架构、SSO、完整 BPMN、打印/PDF、消息中心、专用 ERP/排产模块和大规模集群运维。这些能力不能阻塞首个公开版本。

完成标准：新开发者只根据公开 README，在干净环境完成启动、打开合成示例、修改并发布模板、填写和重开记录，并能运行 CI 同等检查；隐私扫描不包含已知公司或个人标识。

### 阶段 3：通用扩展能力

目标：让项目从“可运行示例”成长为“可被社区二次开发的稳定底座”，优先通用扩展点而不是内置更多业务模块。

候选内容按以下顺序推进：

1. 稳定并版本化模板、业务模型、规则和运行 API；提供 JSON Schema/OpenAPI 或等价机器可读契约。
2. 建立最小插件边界，优先覆盖自定义字段、服务端规则、导入导出和数据连接器；插件必须可禁用且不能绕过权限。
3. 增加固定区域、横向重复和二维交叉区域等通用绑定能力，以独立合成用例验收。
4. 提供模板包的导入、导出、版本升级和兼容检查，使示例与第三方模板不依赖修改核心源码。
5. 提供 HTTP/JSON 与 CSV 等通用连接器；定时任务、重试和对账只为连接器可靠执行服务，不建设完整消息中心。
6. 优化工作区按需加载、分页、公式重算和大表交互，建立可公开复现的性能报告。
7. 根据社区需求评估多人协作；在数据模型、冲突语义和维护成本明确前，不把实时协同列为完成门槛。

阶段 3 明确不做：行业 ERP 模块、复杂组织模型、完整流程中心、内置打印设计器和为了展示数量而堆积连接器。

完成标准：至少一个仓库外扩展示例能够只通过公开契约接入；模板包可以跨干净实例安装；兼容性变化有版本和迁移说明。

### 阶段 4：生态与可选实验

目标：在核心接口稳定后发展社区资源和可关闭的实验能力，不让实验反向污染基础平台。

候选内容：

- 通用模板、规则、函数和连接器示例集合；
- 国际化、无障碍、主题和嵌入式运行模式；
- 社区维护文档、扩展脚手架和版本兼容策略；
- 可选的协作服务、图表或外部报表适配器；
- AI 公式辅助、自然语言建模或 MCP 接口等独立实验插件。

AI、实时协作、图表和报表均为可选扩展：必须可以完全关闭，使用独立依赖和清晰许可证，不成为本地启动、记录保存或模板发布的单点依赖。

完成标准：生态资源与核心版本解耦发布；至少一个外部贡献按公开流程通过 CI；实验插件移除后核心功能和数据仍然可用。

## 14. 阶段 1 验收矩阵

### 14.1 设计端验收

- 普通业务设计人员按操作说明完成常见模板配置，不需要编辑源码、JSON、SQL 或演示初始化脚本；
- 能创建应用和模板；
- 能配置主表、明细表和字段类型；
- 能配置关联表、匹配字段、单条/多条关系、取回字段、筛选条件、汇总口径和实时/快照策略；
- 能预览无匹配、多匹配和权限不足等情况，并配置一条有触发条件的受控回写规则；
- 能从表格中选择单元格或区域进行字段绑定；
- 能设置必填、默认值、选项和公式；
- 能配置基础角色、记录范围和字段状态；
- 能配置简单流程；
- 能用测试数据预览；
- 发布前能发现缺失绑定、无效公式和破坏性结构变化；
- 能发布固定版本并继续维护下一版草稿。

### 14.2 工作人员端验收

- 能打开已发布应用；
- 能直接在已发布模板的类 Excel 网格内录入、复制粘贴和使用允许公式，不依赖另一张普通表单代填；
- 能新增、修改、保存主从记录；
- 保存后刷新或重新登录，数据仍正确；
- 能查询历史记录并按原模板回填；
- 选择供应商或物料后能带出正确资料；关联不因排序、换行或重名而错误；
- 在不同模板中能查询同一业务记录，并按权限、日期和状态得到一致汇总；
- 基础资料变化时实时字段可按规则刷新，历史快照字段不被悄悄覆盖；
- 不同用户看到正确的数据和字段状态；
- 能提交、审批、退回并查看历史；
- 只读人员不能通过 API 绕过权限修改数据。

### 14.3 技术验收

- 前后端单元测试和集成测试通过；
- 关键 API 有权限与参数校验；
- 主从保存事务完整，失败不会留下半条数据；
- 乐观锁能阻止无提示覆盖；
- 关键公式服务端复算结果一致；
- 关联取数、下拉选项、汇总和导出不能泄露无权访问的数据；
- 简单回写失败时事务回滚，重复审批请求不重复更新或生成数据；
- 缺失/多匹配关系、被引用记录停用及规则循环都有明确测试和提示；
- 发布版本可以回滚；
- 审计可定位用户、时间、对象、动作和结果；
- 关键页面完成实际浏览器验收；
- 在基准规模下无明显卡死、崩溃和数据丢失。

### 14.4 产品体验与复用的证据门槛

第 14.1—14.3 节须同时满足；以下场景用于贯穿验收，不新增业务模块，也不取代单项安全及异常检查。

| 场景 | 必须看到的用户动作与结果 | 不可作为替代的证据 |
|---|---|---|
| 配置并发布首个模板 | 设计人员从空白或导入模板出发，通过可视化配置字段、明细、计算和基础规则，预览并发布 | 开发人员运行脚本生成已配置模板 |
| 在模板中填报与重开 | 工作人员打开发布版，在原版式中填写、粘贴多行、使用允许公式、选关联资料、保存并重新打开；记录、明细 ID、结果及权限正确 | 独立字段表单保存成功，或仅有 API 请求结果 |
| 查询及流程处理 | 在权限范围内查历史与汇总、提交/通过/退回，观察字段状态和一条受控回写；越权、重复和失败不破坏数据 | 只展示流程配置、状态字段或按钮 |
| 不改代码配置第二个模板 | 使用相同平台能力配置另一类结构相近模板，复用资料关联、取数、汇总与简单流程；发布后重走填报链路 | 第二份测试数据、复制源码或新增硬编码业务分支 |

每个场景记录模板/发布版本、角色、合成输入、期望值、实际结果、操作步骤和截图或交互记录，并关联对应代码提交。浏览器操作证据与服务端/数据验证证据配套；无浏览器证据时标记待验证。平台验收可用合成数据，不依赖用户提供真实数据；它不能替代后续企业现场适配及试用结论。

## 15. 非功能要求

### 15.1 性能

- 普通模板首屏和常用操作保持可交互；
- 200 列级宽表必须使用可视区域渲染或等效优化；
- 大批量数据不一次性全部加载到浏览器；
- 公式按依赖增量重算；
- 大规模重算进入后台任务，提供进度、取消、超时和失败结果；
- 需要建立 100、1,000、10,000 行以及 200 列宽表的独立基准。

### 15.2 安全

- 所有数据写入、流程操作和导出均服务端鉴权；
- 数据源凭据只保存在服务端并加密；
- 禁止在浏览器或公式中执行任意系统命令；
- 自定义函数和脚本进入沙箱、白名单或独立服务；
- 导入文件进行格式、大小和恶意内容检查；
- 重要操作审计不可由普通用户修改。

### 15.3 一致性与可靠性

- 业务保存使用事务；
- 模板、绑定、规则和发布版本有一致的版本引用；
- 客户端离线或保存失败不能显示为已成功；
- 导入、批量保存和后台计算支持幂等或重复提交保护；
- 备份与恢复必须经过实际演练后才能宣称可用。

### 15.4 可维护性

- 模型、规则和扩展有稳定标识，不以显示名称作为唯一引用；
- 复杂公式优先拆分成可命名、可测试的规则；
- 每项平台能力都有测试样例和兼容说明；
- 历史兼容和迁移逻辑集中管理，不散落在页面组件中。

## 16. 主要风险与控制方式

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 目标继续膨胀 | AI、排产、ERP 模块同时推进 | 以阶段 1 验收矩阵为唯一当前主线 |
| 只做出网页表格 | 有编辑器但无业务数据模型 | 优先完成主从绑定、保存和查询回填 |
| 表格退化为预览附件 | 在普通表单填写，保存后才看原模板 | 核心单据在发布网格中操作，按第 14.4 节验收 |
| 低代码变成开发者工具 | 常见模板仍靠技术 ID、JSON 或初始化脚本配置 | 业务语言配置及第二模板不改代码验收 |
| 用技术测试替代产品验收 | 存储/API 通过就宣称完整闭环 | 分开记录工程、交互和复用证据，未覆盖项不计通过 |
| 过度承诺 Excel 兼容 | 导入后公式或格式静默错误 | 建兼容矩阵、导入报告和明确降级 |
| 平台内核叠加 | 多套 ORM、权限、流程相互冲突 | 每层只保留一个主内核，其他通过接口集成 |
| 超长公式不可维护 | 修改困难、性能差、结果难审计 | 三层计算架构、依赖图和规则拆分 |
| 无真实数据造成假完成 | 合成演示通过但业务不能用 | 区分平台验收与业务适配验收 |
| 前端结果不可信 | 浏览器可篡改关键结果 | 服务端权限、校验和权威复算 |
| 模板升级破坏历史 | 字段删除或改类型导致旧数据异常 | 发布校验、迁移计划、历史版本绑定 |
| 大工作簿卡顿 | 宽表、大量公式、全量加载 | 虚拟化、分片、增量计算和后台任务 |
