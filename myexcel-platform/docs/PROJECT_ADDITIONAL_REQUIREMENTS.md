# 项目额外要求

> 版本：V2.11\
> 更新：2026-09-15\
> 用途：保存跨对话不可丢失的执行约束，不保存产品设计和过程日志。

## 0. 使用方法

开始任务先看下表，只读取与任务相关的规则正文；重大变更或边界不明时再扩大阅读。用户最新明确要求优先，并同步更新相应文档。

| 场景 | 必读规则 |
|---|---|
| 所有修改 | R-001、R-003、R-009 |
| 安装、下载、升级 | R-007 |
| 新需求、材料、架构或范围变化 | R-004 |
| 重大框架/方向选型、复杂关键能力或引入第三方代码 | R-007、R-009、R-010 |
| 第一阶段功能开发 | R-005、R-007 |
| 新增、合并或整理文档 | R-006、R-008、R-009 |
| 跨对话交接 | R-008 |
| 委派辅助 Agent | R-003、R-008、R-009、R-011 |
| 准备公开仓库 | R-001、R-003、R-009、R-012 |

## R-001：Git 与回退

- 修改前检查分支和未提交内容；一个有界成果验证后形成一个可回退提交，不为每次微小编辑单独提交，也不使用宽泛的 `git add .` 混入他人内容。
- 交付时报告提交编号和未覆盖项。未完成只标 checkpoint；完整阶段验收通过后才能建立验收标签，且不覆盖旧标签。
- 公开清理完成前，源码和文档只同步到已确认的私有远程。公开仓库必须按 R-012 使用审查后的干净基线；首次配置或改变可见性由用户确认托管平台、账号、仓库和目标。不得擅自推送到未确认目标，也不得强推、重写历史或清空用户改动。
- 回退前确认目标、依赖和数据影响，优先使用保留历史的撤销提交。
- Git 只管理源码和文档，不管理秘密、依赖、运行数据库、真实业务资料和大体积生成物。代码回退不等于数据库或系统权限恢复。

## R-003：风险分级审查和测试

- 普通文案、链接或状态修正：审阅差异，检查格式、链接和一致性后提交，不要求另写完整计划或运行无关业务测试。
- 有界代码改动：先在当前交接包登记目标、范围和验收；完成后审阅差异，运行与改动直接相关的测试；只有影响构建、接口或发布路径时才构建，记录结果和未覆盖项。
- 架构、技术栈、数据库迁移、权限或高风险改动：先形成方案和回退/数据保护措施，经过所需确认后实施，执行单元、集成、回归及对应实际验证。
- 验证按任务、批次、阶段/发布分层：小改动不运行无关套件；跨模块闭环执行相关集成验证；完整回归、架构一致性审查和完整业务验收只在阶段验收、发布或高风险变更时执行。
- 构建、接口测试和测试数量不能代替真实页面或业务闭环；受阻时标记待验证，不报告通过。
- Codex 自动代码审查已关闭，不作为项目标准流程或交付门槛。执行者按任务、批次、阶段/发布节奏完成匹配的差异审阅和测试；业务验收、文档一致性和架构/范围检查在受影响的批次或阶段执行，不对无关小改重复运行。如以后重新启用，先评估必要性和额度消耗，并仅作为辅助证据。

## R-004：变化先进入规划

- 区分用户明确要求、待确认事项和仅供参考材料；附件、旧方案和其他对话结论不自动成为执行授权。
- 产品目标、架构、技术栈或验收变化更新 `PROJECT_BLUEPRINT.md`；当前任务、状态和证据更新 `PHASE1_PROGRESS.md`；执行约束更新本文件；入口变化才同步 README/AGENTS。
- 明确且有界的变更可在更新规划后执行；存在重大取舍、范围扩大、外部影响或实质歧义时，先向用户说明并等待确认。
- 普通缺陷若不改变既有设计，只需在当前交接包登记目标和验证方式，不修改主设计。

## R-005：第一阶段连续推进边界

- 第一阶段目标仍是通用类 Excel 平台和表间关联完整闭环，不扩展成完整排产、ERP、AI、RAG 或三维图识别项目。
- C-03 当前成果检查通过后，N-01—N-04 按依赖顺序连续推进，不再为每个小阶段重复等待“恢复”授权，也不能并行全部开工。
- 每一小阶段开始前在进度台账用最短可执行形式登记范围、依赖、异常/权限边界、测试、回退和验收；已有基线直接引用，不重复展开。完成相关回归和真实浏览器验收后，收敛缺陷并进入下一小阶段。
- 只有出现范围或架构变化、重大取舍、外部系统/真实数据写入、所需令牌或权限缺失等无法在既定授权内解决的情况时才暂停并请用户处理；一般实现和下载问题由执行对话在既定范围内继续解决。
- 当前原型检查点不代表低门槛配置、表格业务闭环或阶段 1 完成。

## R-006：文档按职责维护

- README 负责简介和导航；主设计负责产品/架构/验收；进度负责当前交接；本文件负责稳定执行约束；环境 README 负责启动操作；AGENTS 负责最小入口和安全提醒。
- 优先修改现有文档。同一内容不能换标题或形式重复建文件；新增文件前必须说明独立读者、用途、生命周期和现有文档无法承载的原因。
- 状态只写一处，其他位置链接。进度台账持续“清旧留新”：关闭批次只保留结论、关键证据入口和仍有效边界，活动批次保留可执行计划；历史由 Git 保存，不另建归档副本。精简时不得删除仍有效的要求、失败或未完成项。

## R-007：统一技术栈

- 所有协作者使用主设计第 11 节的同一版本、模块边界、共享契约、数据库访问、测试方式和锁文件，不得搭建平行技术栈。
- 增加或替换框架、语言、UI 库、ORM、数据库、包管理器、构建体系或升级依赖，必须先更新规划，说明兼容、下载、迁移、回退和验证；重大取舍经用户确认后统一变更。
- Java/JeecgBoot、Nop、Flowable、Redis 等未来候选不构成当前并行开发许可。

## R-008：文档对话与执行对话协作

- 用户、文档规划对话和项目执行对话共同组成闭环，两个对话都直接与用户沟通，但不能自行扩大目标。
- 规划对话主要维护“做什么、边界和验收”：直接修改主设计、长期规则和文档结构；执行对话主要维护“怎么做、做到哪里和证据”：开发、测试并直接修改进度、环境及执行说明。执行对话不得绕过 R-004 改变产品、架构、技术栈或验收。
- 同一时段尽量实行单文件主维护者，另一对话先读取 Git/工作区再改，避免同时编辑同一文档。规划对话不以文字代替完成证据，执行对话不把现场变通默认为新基线。
- 标准循环为：用户确认意图 → 规划落盘 → 执行实施并回写真相 → 规划按证据复核。共享事实只有现行文档、代码、提交和验证结果；稳定规则进本文件，设计进主设计，当前工作进台账，详细历史进 Git。

## R-009：代码与文档保持最小必要

- 代码和文档都以“当前范围内最小而完整、职责清楚、便于维护”为准，不为可能永远不会出现的需求预建功能、抽象、配置、依赖或说明，也不复制已有模块、契约和权威内容。
- 编写代码优先复用现有边界和共享契约，避免平行实现、重复模型、散落工具函数、无调用代码和长期遗留的临时分支；注释说明必要的原因、约束和风险，不逐行复述代码。不得为了少写几行而制造难懂的通用层，或删除错误处理、权限校验、测试和安全措施。
- 编写文档只保留会影响理解、决策、执行、验收或恢复的信息；状态、规则和结论各写一处，其他位置链接引用，不堆叠原始对话、命令输出、重复背景、无结论过程和装饰性文字。
- 新增文件、模块、依赖、公共抽象或文档章节前，必须能说明其当前用途及为什么现有位置不能承载。当前改动产生且已确认不再使用的内容应随本批删除；发现与任务无关的历史冗余时先记录影响，另行规划，不顺手扩大修改范围。
- 提交前除按 R-003 验证外，还要审查本批新增内容是否全部被使用、是否与现有职责重复、是否可以在不降低清晰度和质量的前提下进一步合并或删除；存在必须暂留的重复时说明原因和清理条件。

## R-010：主动调研并合理复用开源成果

- 新项目或现有项目要锁定新的总体方向、架构或技术栈时，至少做一次有时限的开源/相似项目扫描，形成候选比较和采用/改编/借鉴/不采用结论；之后只在三类关口做定向深研：确定或更换重大框架/方向；实现复杂、关键或预计成本较高的能力；既有路线反复失败或出现明确技术未知。普通小模块、既定方案内功能、界面调整、缺陷和文档直接沿用现有工程，不逐节点搜源码。
- 扫描至少覆盖相似产品、框架/组件、数据/架构模式和质量/安全/运维实践；以官方仓库、文档、许可证、发布记录和问题跟踪为主要证据，设置停止条件，不无限下载或浏览。只有短名单通过规模、许可证和安全检查后才构建或引入代码。
- 优先复用本项目已有调研；需求、关键假设、候选版本或风险没有实质变化时不重做选型。定向回答当前决策后即进入验证或实现，不无限扩展候选。
- 区分借鉴思路、改编代码和引入依赖。后两者必须理解行为并核查官方仓库、当前版本、许可证/NOTICE、安全、维护状态、兼容、下载体积、磁盘占用、性能、升级与二开成本；锁定可复现版本、隔离适配边界并保留替换路径，遵守 R-007 的统一技术栈和依赖变更要求。
- 只记录采用/不采用结论、理由、风险和验证方式；稳定选型进主设计，当前取舍进台账，普通浏览不长期保存。开源成果不能代替本项目测试、场景验收和回退评估，也不得为“使用开源”引入平行技术栈或多余抽象。

## R-011：辅助 Agent 的能力分级与交接

- 辅助 Agent 可以获得整个仓库的读取权限并按需查看项目内容，使局部工作符合整体设计；“了解整个项目”不等于把所有文件一次性塞入提示词。默认先给出 README、进度第 2—6 节、适用规则、主设计相关章节、共同基线提交、任务边界、允许修改的文件、预期产物和验收方式，再允许其在仓库内按需追查依赖。
- 能力或成本较低的辅助模型适合承担边界明确、低风险、输出容易复核的部分，例如代码/文档定位、只读扫描、资料整理、重复性检查、已有模式下的局部实现、测试样例和夹具补充。是否委派同时比较节省的时间/Token 与任务说明、复核和返工成本；复核成本可能更高时由主对话直接完成。
- 产品与需求解释、总体架构和技术栈决策、跨模块契约、权限与安全策略、数据库迁移和一致性、破坏性操作、复杂疑难问题、范围调整、最终整合及验收不得交给较弱辅助模型独立决定或独立完成。辅助 Agent 可以调查、提出方案或完成受控子项，但主对话保留判断、整合和责任。
- 辅助 Agent 不是项目中的第三个权威对话，不直接改变产品基线、阶段范围或用户决定。它向委派它的文档规划对话或项目执行对话返回结果；主对话核对代码、差异、来源和测试后，再按 R-008 写入现行文档和 Git，并继续与用户对接。
- 委派任务必须说明“要做什么、不做什么、可改范围、完成标准、验证方法和需上报的不确定项”。交付至少报告查看/修改的文件、实际结果、验证证据、未覆盖项和风险；不得把辅助模型的完成声明直接当作事实。
- 多个 Agent 同时工作时优先分配互不重叠的文件或只读任务；写入任务使用独立分支/工作区或其他可核对边界，未经协调不得同时修改同一文件。不得向辅助 Agent 提供不必要的秘密、真实业务数据或生产权限，仓库可见不代表这些受保护内容也应共享。

## R-012：公开仓库与隐私清理

- 项目公开前必须扫描当前跟踪文件、构建产物、文档、配置、示例、日志和 Git 历史，移除公司名称、品牌、账号、个人路径、内部地址、秘密、真实资料及能够反推出这些内容的截图或备份。
- 删除当前版本中的内容不会删除 Git 历史。默认保留现有私有仓库作为历史归档，从经过审查的源码树建立新的公开初始提交；若要改写现有历史，必须另行说明影响并取得明确授权。
- 公开仓库只包含可再生成的合成数据和通用示例。测试、演示和文档不得依赖用户提供的工作簿、现有业务数据库或本机固定目录。
- 仓库切换为公开可见、创建公开 release 或推送到新的公开远程属于外部发布动作；必须在许可证、第三方 NOTICE、隐私扫描和发布差异均通过后，由用户确认目标仓库再执行。

## 维护原则

- 新要求从 R-013 起编号；修改既有规则保留编号。
- 只在规则实质变化时更新版本。旧版本和变更过程查看 Git，不在本文追加长变更表。
- 临时桌面汇报材料不纳入日常维护；确需长期保留时按 R-006 评估。
