# 可复用项目过程资产

> 版本：V1.4
> 用途：为新项目提供一套可裁剪的规划、执行、验证、交接和维护方法。
> 边界：这是通用方法，不替代具体项目的需求、架构、技术栈、验收或用户授权。

## 1. 使用原则

项目开始时，不只交给执行者一句“做什么”，还要同时提供：

1. 要解决的问题、目标用户和可观察结果；
2. 当前范围、明确不做的内容和优先级；
3. 技术、数据、账号、设备、时间和合规约束；
4. 可复现的验收条件、证据要求和回退边界；
5. 本过程资产，再加上项目自己的权威文档。

本资产采用“最小必要流程”。小任务不套用完整项目仪式；架构、数据、权限、外部系统和不可逆操作必须提高审查等级。流程的目标是减少返工和失真，不是增加文档数量。只有发现重复、过时、职责变化或已经影响执行时，才集中删除、合并或降级步骤和记录。

## 2. 信息分层：每类事实只有一个维护位置

| 信息 | 唯一维护位置 | 内容 |
|---|---|---|
| 项目入口 | `README.md` | 项目是什么、如何开始、文档导航 |
| 长期设计基线 | 项目主设计文档 | 目标、范围、架构、技术栈、领域模型、路线和验收 |
| 当前真实状态 | 当前进度台账 | 做到哪里、证据、阻塞、下一步和未覆盖项 |
| 稳定执行规则 | 项目额外要求 | Git、权限、数据、测试、协作、下载和风险规则 |
| 环境操作 | 环境文档 | 安装、启动、停止、端口、账号和排障 |
| 自动化入口 | `AGENTS.md` 或同类入口文件 | 执行前必读内容和最小安全边界 |
| 历史过程 | Git 提交、标签和发布记录 | 不在当前文档堆叠旧日志 |
| 通用方法 | 本过程资产 | 可复制到新项目并按项目调整的方法和模板 |

同一事实不要在多个文件重复维护。其他文件只保留短说明和链接；项目文档优先于本通用资产，用户最新明确决定优先于旧文档。

## 3. 项目生命周期

### 3.1 立项：先说明为什么做

最少回答以下问题：

- 谁遇到什么问题？现在如何处理？
- 成功后谁会以什么方式受益？
- 第一阶段必须交付的最小结果是什么？
- 哪些内容明确不属于当前项目？
- 现有系统、开源项目、数据和环境可以复用什么？
- 不能做或暂时不能验证的事情是什么？

只写能影响决策、实施或验收的背景。参考材料、历史聊天和示例数据必须标注为“参考”或“已确认要求”，不能自动变成执行授权。

### 3.2 规划：建立可执行基线

规划文档至少固定：

1. 产品定位与用户视角；
2. 当前阶段目标、非目标和优先级；
3. 核心业务对象、数据关系和关键流程；
4. 总体架构、模块边界、接口契约和技术栈版本；
5. 外部依赖、环境条件、权限和数据安全边界；
6. 阶段路线、纵向小闭环及每批验收标准；
7. 主要风险、取舍、回退和仍待确认事项。

规划只描述“做什么、为什么、做到什么算完成”。不要把实现过程、每次命令输出和临时判断塞进主设计。

### 3.2.1 启动时必须做一次开源/相似项目扫描

新项目或现有项目准备锁定新的方向、架构或技术栈时，先做一次有时限扫描，覆盖相似产品、底座组件、架构/数据模式和质量安全实践。记录候选、适用范围、缺口、许可证/维护/安全风险、采用方式、验证结果和证据；设停止条件，短名单通过检查后才下载或引入代码。既有路线内的小任务直接继承已确认结论。

### 3.3 选择路线：先复用成熟成果，再决定自研

把研究分成三层，避免“完全不调研”和“每个任务都调研”两个极端：

1. **路线扫描（新路线必做一次）**：在锁定新方向前完成 §3.2.1 的候选比较，形成路线基线；
2. **定向深评（按需）**：在更换重大框架/方向、实现复杂关键能力、引入第三方代码或既有路线反复失败时，针对当前决策深入验证；
3. **日常实现（不重复搜索）**：普通界面、缺陷修复和既定架构内的小功能沿用已确认路线，除非出现新的技术未知或风险变化。

研究结论只保留会影响决策的内容：采用什么、解决什么、不能解决什么、许可证和维护风险是什么、如何验证，以及不采用候选的原因。评价至少覆盖业务/技术匹配、成熟度、许可证、安全、集成退出和运维成本。借鉴思路、改编代码、直接依赖或外部服务是不同的复用方式；不能把“看过源码”写成“已经采用”。

项目生命周期不是必须逐阶段串行执行的固定仪式。问题已经明确、风险很低时可以缩短探索；技术验证和需求澄清可以并行，但进入实现、发布或验收前必须满足对应出口条件。

采用或改编时锁定版本/提交、记录来源和许可证，隔离适配层，补充契约测试并保留替换路径；不得整仓库复制或引入平行技术栈。架构、技术栈、数据库、权限、公共 API 或关键依赖等难以回退的取舍，用轻量 ADR 记录背景、候选、决定、后果和验证；小项目无此类取舍时不新增 ADR 文件。

### 3.4 拆分：按可验收的纵向切片推进

不要按“前端全部做完、后端全部做完、最后再联调”拆分。每个小阶段应覆盖一条真实业务闭环，例如：

> 配置或输入 → 保存 → 服务端处理 → 查询/展示 → 异常处理 → 权限边界 → 可回退结果

每个小阶段只登记一段有界计划：

```text
目标：本批要让谁完成什么动作
不做：本批明确排除什么
就绪条件：范围、依赖、验收、测试和回退条件已明确
依赖：必须已有的接口、数据、环境或权限
边界：异常、权限、数据和兼容性要求
验证：自动测试、构建、真实页面/业务路径
回退：代码、配置、迁移和数据如何恢复
完成：什么证据齐全后才能进入下一批
```

优先连续完成一个小闭环，再进入下一个；不要为了“看起来进度快”并行打开大量未完成模块。

每批只保留少量可在当前周期内完成和复核的在制品；探索、实现、审查和验收应有明确状态，不以“已经开始”代替“可以交付”。

### 3.5 实施：沿基线最小实现

实施前检查：

- 当前分支、工作区、最近提交和已有用户改动；
- 任务是否改变目标、范围、架构、技术栈、数据或验收；
- 将要修改的文件是否与其他协作者重叠；
- 所需依赖、账号、端口、数据库和测试数据是否可用。

如果需求或材料改变了设计基线，先更新正确的规划文档，再实施。若只是既有设计内的普通缺陷，可以在当前台账登记目标和验收方式后直接修复。

实现时优先复用现有模块、共享契约、错误处理和测试模式。不要为尚未需要的场景预建抽象、配置、依赖或平行内核。

### 3.6 验证：按风险和交付节奏取最小充分证据

不是每个小改动都执行完整回归。按任务、批次和阶段选择验证深度：

| 节奏 | 适用范围 | 最低验证 |
|---|---|---|
| 任务级 | 文案、局部修复、单模块小改 | 差异/格式检查和直接相关测试；不运行无关套件 |
| 批次级 | 跨模块闭环、接口、配置或数据库变化 | 相关自动测试、必要构建和一条关键业务路径 |
| 阶段/发布级 | 阶段验收、高风险变更或对外发布 | 集成/回归、完整业务路径、文档/配置/回退和备份一致性 |

自动层包括单元、接口、集成、迁移、构建和静态检查；业务层覆盖成功、失败、权限和数据一致性；交付层确认文档、配置、版本、启动方式、回退和远程备份。测试数量、构建通过或模型自检都不能单独证明业务完成。无法验证的部分要写成“未覆盖/待验证”，不能写成通过。

安全和维护检查贯穿生命周期：立项识别数据与权限边界，设计限制信任关系，实施避免秘密和不必要依赖，验证覆盖越权/异常/恢复，发布检查配置与供应链，运行阶段处理漏洞、备份、日志和事件。

测试默认使用隔离临时数据库和合成数据；不得向真实业务库写样本。涉及数据迁移时，先说明备份、恢复、兼容窗口和失败处理。

### 3.7 收口：提交、交接、发布

一个有界成果完成并验证后：

- 审阅实际差异，删除无用代码、文档、日志和临时文件；
- 只暂存本批文件，形成可回退提交；
- 更新当前进度台账，记录事实、证据、未覆盖项和下一步；
- 需要时同步远程私有备份；
- 只有完整阶段验收通过后才建立验收标签；未完成只能使用检查点标签；
- 向下一位协作者交接“读什么、改什么、验什么、不要改什么”。
- 发布后根据反馈、缺陷、交付周期、返工和未覆盖项决定下一批，不机械执行已经失效的原计划。

## 4. 文档协作与职责

### 4.1 用户、规划和执行三方闭环

- 用户：确认目标、优先级、授权、取舍和最终接受结果；
- 规划对话/负责人：维护产品、架构、技术栈、范围、验收和文档结构；
- 执行对话/负责人：实施代码、环境和测试，记录实际结果、证据、偏差和阻塞。

规划与执行可以分别直接和用户沟通，但共同事实只能来自现行文件、代码、提交和验证结果。未落盘的聊天内容不能当作另一方已经知道的事实。

### 4.2 变更先归类

收到新需求、附件或纠偏时，先判断它属于：

- 参考信息：帮助理解，但不改变范围；
- 产品/架构/技术栈/验收变更：先更新主设计并确认；
- 当前任务或证据变化：更新进度台账；
- 稳定执行规则变化：更新额外要求；
- 环境操作变化：更新环境文档。

没有必要的范围扩展不要顺手实现。重大取舍、真实数据写入、外部权限、不可逆操作或高风险迁移需要在行动前明确确认。

### 4.3 辅助 Agent 分工

辅助 Agent 可读取完整仓库以理解上下文，但不需要把所有内容一次塞入提示词。默认给它入口文档、相关章节、任务边界、可修改文件、产物和验收方式，再允许按需追查。

适合委派：只读扫描、定位、资料整理、重复性检查、已有模式下的局部实现、测试样例和夹具。

不适合独立委派：产品解释、总体架构和技术栈决策、跨模块契约、权限与安全、数据库迁移、破坏性操作、复杂疑难问题、最终整合和验收。

每次委派必须说明“做什么、不做什么、可改范围、完成标准、验证方法、不确定项如何上报”。主负责人必须复核差异、来源和测试后，才能把结果写入正式文档。

## 5. Git、备份与回退

### 5.1 最小 Git 纪律

- 修改前看分支、工作区和最近提交；保留已有用户改动；
- 不使用宽泛的 `git add .` 混入无关内容；
- 一个有界成果形成一个可理解的提交；普通文档微调可合并，不为每行编辑单独提交；
- 提交信息说明结果，不写“完成全部工作”这类无法核验的表述；
- 阶段验收标签不可覆盖，检查点与验收标签含义分开；
- 不提交秘密、依赖目录、运行数据库、真实业务资料和大体积生成物。

### 5.2 远程备份与恢复

远程备份必须使用用户确认的仓库、账号、可见性和权限。验证后的阶段成果和检查点同步远程；推送不是验收，远程存在也不代表数据库已经备份。

回退前确认：目标提交、影响文件、配置和迁移依赖、运行数据影响、恢复方式以及是否会覆盖其他人的改动。代码回退不等于数据恢复；数据库和外部系统必须有独立恢复方案。

## 6. 风险、权限与数据

风险按影响而不是按代码行数判断：

| 等级 | 典型内容 | 最低要求 |
|---|---|---|
| 低 | 文案、链接、只读定位、既有模式的小修复 | 差异审阅、格式/链接检查、相关测试 |
| 中 | 有界功能、接口、页面状态、配置和普通依赖 | 先登记范围和验收，自动测试、构建和关键业务路径 |
| 高 | 架构、技术栈、权限、真实数据、迁移、外部授权、删除或不可逆操作 | 方案、备份/回退、必要确认、集成回归和实际验收 |

最小权限原则：只申请当前任务所需的账号、仓库、数据库和网络访问；完成后撤销临时权限。日志和截图不得泄露令牌、密码、个人数据或真实业务资料。

### 6.1 质量、发布和持续维护基线

除功能正确外，每个可交付阶段还应明确：

- 可测量的功能和非功能验收，以及哪些风险仍未覆盖；
- 依赖、配置、数据库迁移和数据恢复的发布顺序；
- 失败时的回滚路径、日志/监控和责任人；
- 发布后的反馈、缺陷、漏洞和依赖更新如何回到台账或下一批计划。

质量工具是风险信号，不是形式门槛。可以借鉴自动化安全评分、依赖扫描和代码审查，但结果必须结合本项目的范围、数据和实际验收解释。

## 7. 上下文和维护效率

采用渐进式阅读：

1. 先读入口 README 和当前台账的交接章节；
2. 再读本任务适用的规则；
3. 仅在改变设计或遇到边界时读取主设计相关章节；
4. 只有全面审查才通读长文档和历史。

当前台账只保留正在影响执行的事实、证据入口和下一步；关闭的小阶段清旧留新，详细过程交给 Git。文档写结论、边界、证据和恢复方法，不堆原始对话、重复背景和无结论日志。

如果本批新增或改变了文档职责、规则或结构，再检查三件事：新内容是否被使用？是否与已有职责重复？删除或合并会不会损害正确性、可读性、测试或安全？只有触发结构性复盘时，才进一步检查用户结果、失真判断和下一批应保留/删除/调整什么。指标只服务于改进，不为追求指标增加会议或记录。

## 8. 按项目规模裁剪流程

### 小任务（数小时至数天）

使用 README/任务说明 + 一个有界计划 + 相关测试 + 一个提交。没有架构、数据、权限或外部影响时，不新增完整主设计。

### 中型功能（多个模块或多人协作）

使用完整文档分层、共享契约、阶段台账、隔离测试、业务验收、远程备份和交接记录。每批仍以纵向小闭环收口。

### 高风险或长期项目

在中型流程上增加决策记录、威胁/数据影响评估、迁移与灾备演练、发布审批、监控和回滚演练。只有实际需要才增加专门文档，不为形式创建空模板。

## 9. 新项目启动清单

```text
[ ] 明确问题、用户、成功结果、非目标和第一阶段最小闭环
[ ] 确认用户、数据、设备、账号、合规、时间和网络边界
[ ] 新项目或需要锁定新路线时完成一次有时限的开源/相似项目扫描
[ ] 形成候选比较表，区分直接采用、受控改编、只借鉴和不采用，并记录来源/许可证/验证方式
[ ] 对架构、技术栈、数据、权限或关键依赖取舍建立 ADR 或等价决策记录
[ ] 建立 README、主设计、进度台账、额外要求和环境文档
[ ] 固定技术栈、模块边界、接口/数据契约和验收证据
[ ] 配置 Git 分支、提交策略、私有远程备份和恢复边界
[ ] 登记第一个有界纵向小阶段，不并行铺开全部功能
[ ] 使用隔离环境和合成数据验证成功、失败、权限和一致性
[ ] 提交、更新台账、同步远程，并明确未覆盖项
[ ] 阶段验收后再建验收标签；仅在触发结构性复盘时裁剪流程
```

## 11. 资产自身的维护

本文件只在方法发生实质变化时更新版本。新增章节前，先确认它有独立读者、职责和生命周期，且现有章节无法承载；普通补充应合并到现有位置，不为形式创建文件或章节。

文档整理不是每次任务的固定步骤。仅在发现内容重复/过时、职责或范围发生变化、文档已经影响执行、用户要求，或需要进行阶段性结构复盘时，才盘点并：删除被取代或无执行对象的内容；合并同一事实；把项目特有内容移回对应文档。项目复制本资产后先裁剪，再补充；详细历史由 Git 保留。文档变短不是目标，减少误读、重复和过期信息才是目标。
